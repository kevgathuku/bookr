Docker dress rehearsal

Win: the app you verified locally runs from images on a clean machine — the last step before any cloud.

Everything so far ran on your machine, with your database, your environment, your luck. The dress rehearsal removes all three: build images, boot the production compose file, migrate as a one-off, seed, and prove the whole flow against containers. Then destroy everything and prove it again from zero — if it is not green from scratch, it is not shippable.

Step 1 — The image, layer by layer

uv add gunicorn (frozen lockfile — reproducible builds start here), then a three-stage Dockerfile where every stage justifies itself: a Node stage builds the member SPA (Django serves it same-origin, so the image needs it); a uv sync --frozen --no-dev builder stage resolves locked Python deps (no dev tools in production); a slim runtime stage runs as non-root, bakes collectstatic at build time, and serves config.wsgi with gunicorn. One rule over all of it: no secrets in the image — SECRET_KEY, DATABASE_URL, everything arrives as environment. Verify with docker inspect: the Env list must contain none of them. (The build-time collectstatic needs dummy values to import settings — visibly fake ones, passed only to that one RUN line.)

Step 2 — Prod compose: web, worker, beat

docker-compose.prod.yml grows db, redis, web, worker, and beat. Dev keeps the db-only file and the runserver; prod gets gunicorn plus CELERY_EAGER=0 (the default-eager setting from lesson 5 flips here — tasks must leave the request path in production). Pin a distinct project name:: without it, up replaces the dev database container, because both files define a db service and default to the directory name. That exact accident is why the runbook exists. Migrations are a one-off, never part of boot:

docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml run --rm web python manage.py migrate
docker compose -f docker-compose.prod.yml run --rm web python manage.py seed_demo --e2e-only

The --e2e-only flag seeds just the fixed org (no faker demo users — and faker imports lazily for the same reason, so the seed command runs in an image without dev dependencies).

Step 3 — Verify like a stranger, then destroy it

Pretend you have never seen this app: /healthz → 200, admin login works, book → cancel → refund visible through the containers. Expect the rehearsal to find real bugs — here it found three: the mail outage that 500'd cancels (lesson 5's best-effort notices), the shared compose project name, and the seed's hard faker dependency. Then the proof: down -v, rebuild, migrate, seed, green again. Write docs/rollback-runbook.md now — previous image tag plus how migrations go backwards — before you need it, because needing it is the wrong time to design it.

Exercises

1. Inspect the image layers and justify each one out loud. Remove one and show what breaks.
2. docker inspect the Env: prove no secret baked in. Then break the rule deliberately (hardcode one) and watch the lesson it teaches.
3. Roll back a migration on the compose database following your own runbook. Time yourself.
4. Kill Redis mid-booking with eager off. What does the user see, and which line decides it?
