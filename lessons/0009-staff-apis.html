Staff APIs

Win: every back-office operation the front desk needs — substitutions, catalog, policies, grants, roster actions, member lookup, partner management — as typed, venue-scoped, staff-gated endpoints.

Member endpoints guard money; staff endpoints guard operations. The threat model differs: a staff credential reaches across members, so every endpoint here is venue-scoped (404 outside), staff-gated (a second permission on top of membership), and typed (400s name the problem, never 500s). Two permissions you will reuse on every view: IsVenueMember (covering membership or 404) and IsStaff / IsStaffOrReadOnly (writes need a covering staff role; reads need membership alone).

Step 1 — Substitutions, products, policies

POST /api/v1/substitutions/ takes a class and a new teacher and flips both the roster and the history row in one transaction: old_teacher is filled from the class (never trusted from the client — a crafted past teacher would forge history), created_by from the request user, 400 on same-teacher or non-scheduled classes. History rows expose old_teacher_name → new_teacher_name so readers never join.

PassProductViewSet is full CRUD minus DELETE — issued passes PROTECT their product, so deletion is refused at the database, and the viewset simply offers no route. The venue comes from tenancy, never the payload: perform_create saves with request.venue, so a crafted venue id cannot file products elsewhere. Policies are versions, never edits: GET /api/v1/policies/ lists history, POST /api/v1/policies/activate/ retires the open row and inserts the successor with the next version number, atomically. Overlapping open rows are allowed; holders pin versions explicitly (see step 4).

Step 2 — Grant, adjust, and the roster actions

POST /api/v1/passes/grant/ takes member and product ids and returns the pass plus its purchase row — the staff sale. POST /api/v1/ledger/adjust/ takes pass, non-zero delta, and a mandatory reason; the text lands on the ledger row's note next to the machine reason, because auditors filter by one and read the other.

The desk trio operates on bookings by id, venue-scoped 404 like everything else: POST .../checkin/ stamps confirmed bookings, POST .../no-show/ marks inside 2h after end (outside that window it refuses — the rule, not the clock, decides), and cancel accepts {"staff_override": true, "reason": ...} with the reason mandatory. GET /api/v1/bookings/roster/?date= lists the day's bookings with member and class info for the roster screen; GET /api/v1/members/search/?q= finds venue and spanning members by username fragment (capped at 20 — unbounded search is a latency incident), returning ids the grant and adjust forms need; GET /api/v1/passes/?member= lists one member's passes for the same forms. Read-only catalog lists (/rooms/, /class-types/) feed the class-create form.

Step 3 — Partner back-office

Lesson 12 builds the partner channel; this lesson builds its back-office, because partners are managed by staff, not by partners. POST /api/v1/staff/aggregators/ creates the partner, its service user, and a hashed token — returning the raw token exactly once in the response (it is never stored, so this viewing is the only one that will ever exist). POST .../<slug>/rotate/ replaces the hash, invalidating the old token everywhere immediately. GET .../<slug>/events/ reads the reconciliation log the channel writes on every call — the same rows lesson 12's replay test walks.

Step 4 — Policy versions and grandfathering

Policy rows carry a per-venue version sequence (system-assigned on save — staff never pick numbers). Memberships carry an optional policy foreign key: null follows the venue's current version (the latest open row), set pins the holder — later activations never move them. Resolution (Venue.policy_for(user)) prefers the venue-pinned membership, then a spanning one, then current. Cancel windows, waitlist holds, and appointment cutoffs all resolve through it; the availability buffer stays venue-level (no member in scope). No backfill migration was needed — null already means current, and writing foreign keys for everyone would have frozen them to today's version, defeating every future activation. Deleting a pinned version is PROTECTed: history with holders must not vanish.

Exercises

1. Forge a substitution with a invented past teacher through the API. Which layer refuses, and what does the row show afterward?
2. Rotate a partner token, then replay an old-token request. Prove 401 — then find the event-log row for the attempt (or explain its absence).
3. Pin a member to v1, activate v2 with a tighter window, and cancel the member inside v1's window but outside v2's. Which status results, and why?
4. Search members with an empty query as staff, then as a member. Compare the two status codes and explain each.
