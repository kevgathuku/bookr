Credit ledger

Win: every credit movement is an append-only row, the balance is always the sum, and booking spends inside the same transaction as the seat.

Lessons 4 and 5 booked and ended seats without money — deliberately. This lesson adds the wallet and wires it into exactly the two seams left open: the charge in _create and the charge in _promote, plus refunds on the cancel paths. The core rule fits in one sentence: balance is always SUM(delta). The credits_used counter you will see on the pass is a cache for reads, updated in the same transaction as the row — never edited directly, never trusted over the sum.

Step 1 — New app, three models

uv run python manage.py startapp passes

PassProduct is the catalog (venue-scoped names, like lesson 3's types and rooms): limited packs carry a credit count, unlimited ones carry null — null means infinite, zero would mean empty, and confusing the two is a classic bug, so read is_unlimited twice:

class PassProduct(models.Model):
    objects = VenueScopedQuerySet.as_manager()
    venue = models.ForeignKey(
        "organizations.Venue", on_delete=models.CASCADE, related_name="pass_products"
    )
    name = models.CharField(max_length=200)
    credits_total = models.PositiveIntegerField(null=True, blank=True)
    validity_days = models.PositiveIntegerField()
    applicable_class_types = models.ManyToManyField(
        "scheduling.ClassType", blank=True, related_name="pass_products"
    )
    transferable = models.BooleanField(default=False)

MemberPass is one sold copy: member, product snapshot (credits_total copied at sale so later catalog edits never rewrite history), validity window, status, and the cached counter. CreditLedger is the money itself — every row carries the pass, the optional booking it settles, a signed delta, a machine reason, and a human note:

class CreditLedger(models.Model):
    class Reason(models.TextChoices):
        PURCHASE = "purchase", "Purchase"
        BOOKING = "booking", "Booking"
        REFUND = "refund", "Refund"
        FORFEIT = "forfeit", "Forfeit"
        EXPIRY = "expiry", "Expiry"
        ADJUSTMENT = "adjustment", "Adjustment"

    member_pass = models.ForeignKey(
        MemberPass, on_delete=models.PROTECT, related_name="entries"
    )
    booking = models.ForeignKey(
        "booking.Booking",
        on_delete=models.SET_NULL,
        null=True,
        blank=True,
        related_name="settled_bookings",
    )
    delta = models.IntegerField()
    reason = models.CharField(max_length=16, choices=Reason.choices)
    note = models.CharField(max_length=280, blank=True, default="")
    created_by = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.SET_NULL,
        null=True,
        blank=True,
        related_name="+",
    )
    created_at = models.DateTimeField(auto_now_add=True)

Why a closed reason taxonomy plus a free-text note? Reports and reconciliation group by reason — "show me all refunds" must be a filter, not a text search. Humans write notes — "goodwill, front desk" explains why to the next staffer. One field cannot do both jobs; two fields can. And PROTECT on the pass (not CASCADE): money rows must survive their pass, or the audit trail develops holes exactly when it matters.

Step 2 — Spend, refund, adjust, expire

Oldest-valid-first, unlimited before limited — deterministic choice matters because tests must predict which pass gets charged:

def spend_credit(member, booking):
    """Oldest-valid-first, unlimited before limited. Must run inside the
    booking transaction (row locks serialize the last-credit race). Returns
    the ledger row, or None for unlimited (nothing to deplete)."""

That docstring's first sentence is the whole concurrency story: the candidate passes are locked with select_for_update, so two simultaneous spends on the last credit serialize — the loser sees the depleted pass and fails instead of double-spending. Refund is the mirror (plus one, reactivated from depleted), adjust is the staff correction (mandatory reason, non-zero delta enforced — service here, HTTP endpoint in lesson 9 with the other staff operations), and expiry zeroes lapsed balances on the beat. Every one of them runs inside a transaction with locked rows; money functions that run outside transactions are how ledgers drift from reality.

Step 3 — Wire the two seams

Open booking/services.py and fill the marked spot in _create: after the row is created, if confirmed, spend — inside the same transaction, so CreditInsufficient rolls the booking back too and nothing is ever written half-done. Waitlisted bookings spend nothing yet (no seat, no charge — promotion charges later). Unlimited passes spend nothing and leave credit_tx empty. Then the same single line in _promote, and refund_credit on the cancel path from lesson 5. Three one-line edits, each with a test that fails first: book-with-no-credit aborts with no row, promotion with a lapsed pass stays queued, cancel restores the credit with a refund row.

Step 4 — Member endpoints

GET /api/v1/me/passes/ (own passes, all venues) and GET /api/v1/ledger/ (own entries; staff see the venue's — the same view serves both by role, which lesson 9's desk reuses). No DELETE anywhere near money: products with issued passes are PROTECTed, and ledger rows are append-only by construction — there is simply no endpoint that removes them.

Exercises

1. Last-credit race: two threads, one credit, same member. Prove one CreditInsufficient and a balanced ledger — then remove the select_for_update and watch it break.
2. Expire a pass with a remaining balance mid-hold and sweep. Who gets what, in which order?
3. Change the spend order to newest-first. Which existing test fails, and is the failure testing behavior or implementation?
4. Unlimited pass, expired window: book. Which guard refuses, and why must validity outrank unlimitedness?
