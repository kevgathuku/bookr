Door access

Win: a controller at the door admits members with live bookings or active passes — and denies everything else, including the database being down.

Physical access inverts every assumption so far: the unhappy path is the safe path. A booking page that errors is an inconvenience; a door that opens on error is a break-in. So this lesson builds one pure decision function with a single overriding rule — any outage denies — plus the token-scoped API controllers use, an event log of every identified attempt, and a Prometheus counter for the dashboard.

Step 1 — Points, tokens, and events

AccessPoint is a door: venue, name, controller id (unique per venue), a hashed controller token, and a passback window. Tokens follow the same rule as lesson 12's partner tokens will: set_token() returns the plaintext exactly once and stores only the hash — if it leaks, rotate it; there is nothing to "remind" you of:

    def set_token(self):
        """Rotate the controller secret. Plaintext shown once, hash stored."""

AccessEvent logs every identified attempt: point, member (nullable — strangers get rows too), granted boolean, machine reason, optional booking. The log is the audit trail and the anti-passback memory in one table.

Step 2 — The decision function

decide(access_point, member) returns (granted, reason, booking_or_None) through an ordered cascade — first match wins, cheapest check first:

1. Passback replay. Same member, same door, inside passback_seconds (60s default): return the prior verdict without a new row. Tailgating protection works both directions — a recent deny replays as deny, so hammering the reader changes nothing.
2. Cached verdict. A 60s cache keyed door:<point>:<member> absorbs reader chatter — but a cached grant re-checks the linked booking's status first, because a member who cancels inside the TTL must not walk in on a stale grant.
3. Fresh evaluation. Active pass → grant. Live booking window (15 minutes around class time) → grant with the booking attached. Covering staff → grant. Else deny with a reason that says which check failed.

And the rule over all of it: any database failure denies. The cache exists for latency, not availability — a down database is a locked door, never an open one. Write the fail-closed drill as a test (mock the database down, assert deny), because the day you need it, it is too late to add it.

Step 3 — Token-scoped check API and the tail

POST /api/access/check/ authenticates the controller (per-point token, not a member JWT — doors are not users), calls decide, logs the event, and bumps door_grants_total{venue_id} on grants. Front desk reads the tail at GET /api/v1/access/events/ (staff-only, newest first, capped at 100 — unbounded tails are a latency incident waiting for a busy Saturday). The Prometheus counter rides on /metrics/ next to /healthz: grants per venue, the one number that tells you the doors are alive.

Exercises

1. Fail-closed drill: break the database connection mid-test and prove deny. Then break the cache instead — what changes?
2. Cancel inside the TTL: grant, cancel the booking, re-check within 60 seconds. Prove deny, then explain which line does it.
3. Passback both ways: grant then deny the same member within the window (revoke the pass between taps). What replays?
4. p95: time 1,000 checks against seed data. Where does the time go — and what does the cache buy you?
