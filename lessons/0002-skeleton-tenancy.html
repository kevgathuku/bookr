4a — Membership: the role lives on the join, not on the user

In organizations/models.py:

class Membership(models.Model):
    class Role(models.TextChoices):
        OWNER = "owner", "Owner"
        MANAGER = "manager", "Manager"
        TEACHER = "teacher", "Teacher"
        FRONTDESK = "frontdesk", "Front desk"
        MEMBER = "member", "Member"

    organization = models.ForeignKey(Organization,
        on_delete=models.CASCADE, related_name="memberships")
    venue = models.ForeignKey(Venue, on_delete=models.CASCADE,
        null=True, blank=True, related_name="memberships")
    user = models.ForeignKey(settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE, related_name="memberships")
    role = models.CharField(max_length=16, choices=Role.choices)

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=["organization", "user", "venue"],
                name="member_once_per_scope"),
        ]

Why this shape: a role is meaningless without its organization — "manager at A, member at B" can't be expressed with Django's global Groups, so the role sits on the join row and Groups stay out of it (reach for them later only if the Django admin needs per-model permissions). Why nullable venue: the organization sets one rule — spanning (venue NULL, covers every venue) or per_venue (venue required, enforced where memberships are created, since a check constraint can't compare across tables). Two sharp edges to know: the unique index is on (org, user, venue), and NULLs never equal in Postgres — so nothing stops two spanning rows for one user; guard that in the creation service (one spanning membership per user per org). App-level checks alone would race; the index makes the loser fail no matter the timing.

4b — Middleware: resolve the venue once, in one place

class VenueMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        request.venue = self._resolve(request)  # None → every scoped view 404s
        # Derive, don't trust: the org always comes from the venue, never
        # from a second header — two client-controlled headers will disagree.
        request.organization = request.venue.organization if request.venue else None
        return self.get_response(request)

    def _resolve(self, request):
        if request.user.is_authenticated:
            # Staff browser sessions carry a user: their (single) venue wins.
            if membership := Membership.objects.filter(
                    user=request.user).only("venue").first():
                return membership.venue
        # API clients (aggregators, door controllers in later lessons)
        # carry no user — only a header. Fall back to it, not the reverse:
        # a logged-in user must never escape into another venue by header.
        if slug := request.headers.get("X-Venue-Slug"):
            return Venue.objects.filter(slug=slug).first()
        return None

Why middleware instead of per-view logic: tenancy is a request-wide fact, and scattering twelve copies of it across views guarantees the thirteenth view forgets. One choke point means every scoped queryset starts from request.venue the same way. Why staff-first, header-second: headers are client-controlled, so an authenticated user must not be able to header their way into someone else's venue.

4c — Permission: deny outsiders with 404, not 403

class IsVenueMember(BasePermission):
    def has_permission(self, request, view):
        if request.venue is None or not request.user.is_authenticated:
            return False
        return Membership.objects.filter(
            user=request.user, organization=request.organization
        ).filter(Q(venue__isnull=True) | Q(venue=request.venue)).exists()

And every scoped viewset filters its queryset to request.venue before permission runs — so an org-B member asking for org-A's class 42, or a venue-B-pinned member asking for venue-A's, gets 404 exactly as if 42 didn't exist. The spanning-or-pinned Q is the whole scope model in one query: org must match, and then either the row covers everything or it names this venue. Why not the more truthful 403: a 403 confirms the object is real, which lets anyone enumerate other organizations' records one id at a time (glossary). A 404 reveals nothing.
