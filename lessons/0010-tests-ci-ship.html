Tests, CI, ship

Win: a suite you trust and a pipeline that runs it — green on a fresh clone, following only this course.

Nine lessons built the product; this one proves it and operates it. Two halves: the E2E harness that tests the running app (not just functions), and the scoped Django admin that lets owners work without API calls. Then the pipeline that runs everything on every push.

Step 1 — Markers: smoke per commit, e2e nightly

Not all tests cost the same, so they do not all run together. pytestmark splits the suite: unmarked backend tests run always; @smoke hits a live server with real Postgres (per commit); @e2e drives a real browser (nightly and pre-release). Declared once in pyproject.toml:

[tool.pytest.ini_options]
markers = [
    "smoke: per-commit end-to-end smoke (live server, no sleeps)",
    "e2e: full nightly/pre-release suite (needs worker, mailpit, frontend)",
]

Step 2 — The harness: boot, seed, serve, smoke

tests/e2e/boot.sh is a script with opinions, and every opinion is stated at the top: migrate, seed (including the fixed --e2e org with known users and short windows), serve, wait on readiness (bounded 60s curl loop — never bare sleeps), run smoke, and kill only what it started. Two rules worth copying into every project: fail if the port is already serving (a stray runserver makes green meaningless), and seed inside the test database with committed rows (the live-server thread cannot see uncommitted test transactions). The browser journey — login, book the only seat, second member waitlists, ledger shows both — runs against the same server the smoke tests hit, with seeded data, no mocks.

Step 3 — Operate: a scoped admin

Django gives you an admin; multi-tenancy takes most of it away and hands back exactly what each role may touch. BookrAdminSite.has_permission gates the whole site on back-office roles (owner, manager, frontdesk — teachers and members are denied even if flagged staff), VenueScopedAdmin scopes every queryset to the requester's venues (same-venue policy inline is the one exception — cross-venue inlines leak), and ReadOnlyAdmin covers the ledger and event logs (money and history are append-only everywhere, including here). The substitution form fills past teacher and recorder from the roster and the logged-in user — fields the form never shows, because history you can type is history you can forge.

Step 4 — Pipeline: gates in order

GitHub Actions with a real Postgres service (not SQLite — lesson 3's constraint must exist in CI too): ruff, format check, mypy, pytest, then smoke. Each gate blocks the next; a red gate stops the line. Secrets in CI are openly insecure dummy values (ci-only-insecure-key) — honest fakes, never almost-real ones.

Exercises

1. Occupy port 8000 and run boot.sh. Read its refusal, then explain what false-green it prevents.
2. Break one admin scope (remove a _scope_q) and write the test that catches cross-venue rows.
3. Make smoke flaky on purpose (a bare sleep instead of readiness). Run it ten times and count the reds.
4. Log in to the admin as a teacher. List everything visible, and justify each item.
