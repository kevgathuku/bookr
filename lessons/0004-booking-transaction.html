The booking transaction

Win: exactly one member gets the last seat, even with 20 racers. If this fails, stop — nothing later matters.

Step 1 — New app, then model

uv run python manage.py startapp bookings, add it to INSTALLED_APPS. Then the Booking: unique idempotency_key, member, nullable class/appointment FKs with a check that exactly one is set (condition= in Django 6), status, source (app/frontdesk/`aggregator:<slug>`), credit link (stubbed until lesson 6). Plus partial uniques — one active booking per member per class:

constraints = [
    CheckConstraint(condition=(
        Q(scheduled_class__isnull=False, appointment__isnull=True)
        | Q(scheduled_class__isnull=True, appointment__isnull=False)),
        name="booking_single_target"),
    UniqueConstraint(fields=["venue", "member", "scheduled_class"],
        condition=Q(status__in=["confirmed", "waitlisted"]),
        name="one_active_class_booking"),
]

This is the primary seam (see testing cheatsheet).

Step 2 — The one function that books

bookings/services.py::book_seat(member, klass, waitlist=False, idempotency_key) — the only code path that creates bookings. Thin views, fat service:

class SeatFull(Exception): ...
class DuplicateBooking(Exception): ...

def book_seat(member, klass, *, waitlist=False, idempotency_key):
    with transaction.atomic():
        klass = ScheduledClass.objects.select_for_update().get(pk=klass.pk)
        status = "confirmed"
        if Booking.objects.filter(scheduled_class=klass,
                status="confirmed").count() >= klass.effective_capacity():
            if not waitlist:
                raise SeatFull  # view → 409, offer ?waitlist=true
            status = "waitlisted"
        booking = Booking(member=member, scheduled_class=klass,
            status=status, venue=klass.venue, idempotency_key=idempotency_key)
        booking.save()
        if status == "confirmed":
            spend_credit(member, booking)  # raises → whole transaction rolls back
        return booking

Views map typed errors to codes: SeatFull→409, CreditInsufficient→402, DuplicateBooking→409. Member login arrives here too (uv add djangorestframework-simplejwt) — the book endpoint authenticates the member; everything else stays service-level. No business logic in views or serializers — ever.

Step 3 — The race test (required)

With 1 free seat, fire 20 threads at book_seat (ThreadPoolExecutor, each with its own idempotency key) and assert exactly 1 confirmed. Then: same key twice → one booking; same member twice → 409. If the race test fails, stop — nothing later matters.
