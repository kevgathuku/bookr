The booking transaction

Win: exactly one member gets the last seat, even with 20 racers. If this fails, stop — nothing later matters.

Lesson 3 pushed the no-double-booking rule into the database. This lesson does the same for the booking itself: one seat, many simultaneous tappers, exactly one winner. The mechanism is a database row lock (SELECT ... FOR UPDATE) inside a single function — book_seat() — that is the only code path allowed to create bookings. Thin views, fat service: every future channel (front desk, aggregators in lesson 12) will call this same function instead of inventing its own booking logic. That is the most important architectural decision in the project, and it happens in this lesson.

Step 1 — New app, then the Booking model

uv run python manage.py startapp booking

Add "booking.apps.BookingConfig" to INSTALLED_APPS. The model (extra targets and money links arrive in their own lessons — each with its own migration, so run makemigrations booking after every step here):

from typing import ClassVar

from django.conf import settings
from django.db import models

ACTIVE_STATUSES = ("confirmed", "waitlisted")


class Booking(models.Model):
    class Status(models.TextChoices):
        CONFIRMED = "confirmed", "Confirmed"
        WAITLISTED = "waitlisted", "Waitlisted"
        CANCELLED = "cancelled", "Cancelled"
        CANCELLED_LATE = "cancelled_late", "Cancelled late"
        NO_SHOW = "no_show", "No-show"
        COMPLETED = "completed", "Completed"

    venue = models.ForeignKey(
        "organizations.Venue", on_delete=models.CASCADE, related_name="bookings"
    )
    member = models.ForeignKey(
        settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name="bookings"
    )
    scheduled_class = models.ForeignKey(
        "scheduling.ScheduledClass",
        on_delete=models.CASCADE,
        related_name="bookings",
    )
    status = models.CharField(
        max_length=16, choices=Status.choices, default=Status.CONFIRMED
    )
    source = models.CharField(max_length=64, default="app")
    idempotency_key = models.CharField(max_length=64, unique=True)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        constraints: ClassVar[list[models.BaseConstraint]] = [
            models.UniqueConstraint(
                fields=["venue", "member", "scheduled_class"],
                condition=models.Q(status__in=ACTIVE_STATUSES),
                name="one_active_class_booking",
            ),
        ]

Four decisions. First, venue is stored on the booking even though the class already has one — derived at creation (venue=klass.venue), never taken from the client, so a crafted payload cannot file a booking under someone else's venue. Second, idempotency_key is globally unique: when a phone retries a tap over a flaky network, the retry carries the same key and gets back the original row instead of a second booking. Third, the partial unique: one active booking per member per class — cancelled rows are exempt, so rebooking after a cancel works. Fourth, source defaults to "app" and you do nothing else with it until lesson 12; it is a free column that will later read aggregator:<slug>.

Step 2 — Typed errors, then the one function that books

Services raise typed exceptions; views translate them to HTTP. Never the reverse — the service layer must not import the web layer, or you can never call it from a Celery task, a management command, or a partner channel:

# booking/errors.py — the whole file. Views map these to HTTP
# (SeatFull/DuplicateBooking → 409); the service never imports the web layer.


class BookingError(Exception):
    """Base for all book_seat() failures."""


class SeatFull(BookingError):
    """Class is full and waitlist was not requested."""


class DuplicateBooking(BookingError):
    """Member already holds an active booking for this class."""

Now the function. Read it as four guards in a fixed order — each guard exists because a real failure demanded it:

# booking/services.py
from django.db import IntegrityError, transaction

from booking.errors import DuplicateBooking, SeatFull
from booking.models import ACTIVE_STATUSES, Booking
from scheduling.models import ScheduledClass


def _active_booking(member, klass) -> bool:
    return Booking.objects.filter(
        venue=klass.venue,
        member=member,
        scheduled_class=klass,
        status__in=ACTIVE_STATUSES,
    ).exists()


def _status_for(klass, waitlist: bool) -> str:
    confirmed_seats = Booking.objects.filter(
        scheduled_class=klass,
        status=Booking.Status.CONFIRMED,
    ).count()
    if confirmed_seats < (klass.capacity or 0):
        return Booking.Status.CONFIRMED
    if waitlist:
        return Booking.Status.WAITLISTED
    raise SeatFull(f"{klass} is full.")


def _create(member, klass, status: str, idem_key: str) -> Booking:
    try:
        booking = Booking.objects.create(
            venue=klass.venue,
            member=member,
            scheduled_class=klass,
            status=status,
            idempotency_key=idem_key,
        )
    except IntegrityError:
        # Lost a same-key race: the winner's row is the answer.
        winner = Booking.objects.filter(idempotency_key=idem_key).first()
        if winner is not None:
            return winner
        raise DuplicateBooking(f"{member} already booked {klass}.")
    return booking


def book_seat(member, klass, *, idempotency_key: str, waitlist: bool = False) -> Booking:
    """Book one seat, serialized per class via SELECT ... FOR UPDATE."""
    with transaction.atomic():
        locked = ScheduledClass.objects.select_for_update().get(pk=klass.pk)

        existing = Booking.objects.filter(idempotency_key=idempotency_key).first()
        if existing is not None:
            return existing
        if _active_booking(member, locked):
            raise DuplicateBooking(f"{member} already booked {locked}.")

        status = _status_for(locked, waitlist)
        return _create(member, locked, status, idempotency_key)

Why this order matters. The row lock comes first: select_for_update makes concurrent transactions for the same class queue up instead of interleaving, so the seat count that follows is always fresh. The idempotency check comes before the duplicate check: a retry is not a double-booking, it is the same booking arriving twice. The IntegrityError fallback in _create covers the one race locks cannot — two requests with the same key racing past the check simultaneously: the loser reads back the winner's row instead of crashing. And notice what is not here: no credit spend (lesson 6 wires the charge into exactly the marked spot), no teacher clash (lesson 7), no channel parameter (lesson 12). Each arrives with its own tests.

Step 3 — Thin view, mapped errors, router

The view validates, resolves the class against the request venue (404 on mismatch — crafted venue ids must not escape), and maps service errors to status codes. mapped_errors is a context manager so the mapping lives in one place (booking/http.py) instead of try/except in every view:

from booking.http import mapped_errors
from booking.services import book_seat


class BookingsView(APIView):
    permission_classes: ClassVar[list] = [IsVenueMember]

    def post(self, request):
        form = BookSerializer(data=request.data)
        form.is_valid(raise_exception=True)
        klass = form.validated_data["scheduled_class"]
        if klass.venue != request.venue:
            raise NotFound("No such venue.")
        waitlist = form.validated_data["waitlist"]
        if request.query_params.get("waitlist") == "true":
            waitlist = True
        with mapped_errors():
            booking = book_seat(
                request.user,
                klass,
                idempotency_key=form.validated_data["idempotency_key"],
                waitlist=waitlist,
            )
        return Response(BookingSerializer(booking).data, status=201)

Register booking/urls.py (POST /api/v1/bookings/) and include it under api/v1/. The BookSerializer takes scheduled_class, idempotency_key, and an optional waitlist flag — the frontend generates the key with crypto.randomUUID() per tap, which is why a retried tap is indistinguishable from its original.

Step 4 — The race test (20 threads, 1 seat)

Helpers first, same style as lesson 3 (_venue, _user, plus a member and a class builder). Then the test that justifies the whole lesson — and the one pytest-django subtlety it needs:

@pytest.mark.django_db(transaction=True)
class TestLastSeatRace:
    def test_twenty_threads_one_seat_yields_one_confirmed(self):
        venue = _venue(slug="race")
        klass = _class(venue, capacity=1)
        members = [_member(f"racer-{i}", venue) for i in range(20)]
        outcomes = []

        def attempt(i):
            try:
                booking = book_seat(members[i], klass, idempotency_key=f"race-{i}")
                return booking.status
            except SeatFull:
                return "full"
            finally:
                # Threads hold their connection open; release it so the
                # test database can tear down.
                connection.close()

        with ThreadPoolExecutor(max_workers=20) as pool:
            outcomes = list(pool.map(attempt, range(20)))

        assert outcomes.count("confirmed") == 1
        assert outcomes.count("full") == 19
        assert klass.bookings.filter(status="confirmed").count() == 1

Two things to learn here. First, transaction=True: the default pytest-django marker wraps each test in an atomic block that never commits — invisible to other database connections, which is exactly what threads are. The transactional marker commits setup for real, so all 20 threads see the same class. Second, connection.close() in the finally: threads hold their connections open and the test database cannot tear down around them — leaked connections are the classic flaky-cleanup bug in threaded tests. Alongside it, write the three single-threaded guarantees: same key twice returns the one booking, same member rebooking raises, and cancelled bookings free both the seat and the member slot.

Exercises

1. Remove the select_for_update call and run the race test five times. Count how often it fails — that frequency is the bug rate you would ship without the lock.
2. Swap the guard order: duplicate-check before idempotency-check. Which existing test breaks, and what user-visible behavior changes?
3. Add a ?waitlist=true end-to-end assertion: fill the class, book with the flag, confirm the waitlisted row and no charge path (there is no charge yet — note where lesson 6 will hook in).
4. What happens when two requests share an idempotency key for different classes? Write the test, then decide whether the current answer (first booking wins) is acceptable.
