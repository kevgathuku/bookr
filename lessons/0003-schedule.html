Schedule that can't double-book

Win: staff publish classes, and the database itself refuses overlapping room or teacher bookings — even when two requests arrive in the same millisecond.

This is the lesson where Bookr stops trusting application code with its most important rule. You could check for overlapping classes in Python: query for clashes, then insert. That works right up until two requests interleave — both check, both see nothing, both insert, and Monday 6pm Spin has two teachers in one room. The fix is to teach the rule to Postgres itself with an exclusion constraint: the database rejects the second insert no matter how the requests overlap. Your job in this lesson is the models, the constraint, the tests that prove the refusal, and the first list endpoint.

Step 0 — Use real Postgres, starting today

Exclusion constraints are a Postgres feature. They do not exist in SQLite, so there is no point developing against SQLite and "switching later" — the constraint would silently never be created. The project runs real Postgres from day one (Docker maps it to host port 5433 because Homebrew Postgres usually owns 5432):

docker compose up -d db
DATABASE_URL=postgres://bookr:bookr@localhost:5433/bookr SECRET_KEY=x \
  uv run python manage.py migrate

Make this a habit: every test command in this course starts with those two environment variables. They will not be repeated in every snippet.

Step 1 — New app, then the catalog models

Create the app and register it. Delete the stub files you will not use yet (admin.py, tests.py, views.py stay empty for now — Django only needs models.py and apps.py in this step):

uv run python manage.py startapp scheduling

Add "scheduling.apps.SchedulingConfig" to INSTALLED_APPS. Then the two catalog models. Everything in this app belongs to exactly one venue — schedules are never shared across venues, so every model carries a venue foreign key and names are unique per venue, not globally (two gyms can both have a "Spin" and a "Studio A"). First, one shared helper at the top of scheduling/models.py — a queryset method for "rows belonging to this venue", so views never repeat .filter(venue=...) (a later lesson centralizes this into a shared tenancy module; for now it lives with the models that use it):

class VenueScopedQuerySet(models.QuerySet):
    def for_venue(self, venue):
        return self.filter(venue=venue)

Now the models themselves:

from typing import ClassVar

from django.db import models


class ClassType(models.Model):
    objects = VenueScopedQuerySet.as_manager()
    venue = models.ForeignKey(
        "organizations.Venue", on_delete=models.CASCADE, related_name="class_types"
    )
    name = models.CharField(max_length=200)
    description = models.TextField(default="", blank=True)
    capacity_default = models.PositiveIntegerField(null=True, blank=True)
    duration_min = models.PositiveIntegerField()

    class Meta:
        constraints: ClassVar[list[models.BaseConstraint]] = [
            models.UniqueConstraint(
                fields=["venue", "name"], name="classtype_unique_per_venue"
            ),
        ]

    def __str__(self):
        return f"{self.name} @ {self.venue}"


class Room(models.Model):
    objects = VenueScopedQuerySet.as_manager()
    venue = models.ForeignKey(
        "organizations.Venue", on_delete=models.CASCADE, related_name="rooms"
    )
    name = models.CharField(max_length=200)
    capacity = models.PositiveIntegerField(null=True, blank=True)

    class Meta:
        constraints: ClassVar[list[models.BaseConstraint]] = [
            models.UniqueConstraint(
                fields=["venue", "name"], name="room_unique_per_venue"
            ),
        ]

    def __str__(self):
        return f"{self.name} @ {self.venue}"

Three decisions to notice. First, VenueScopedQuerySet.as_manager() gives every model a .for_venue(venue) queryset method — one shared helper for "rows belonging to this venue" instead of repeating .filter(venue=...) in every view (you will use it in step 6). Second, the ClassVar[...] annotation on Meta.constraints: ruff's RUF012 rule flags mutable class attributes, and the annotation marks the list as intentional class-level state rather than a mistake. Third, __str__ on every model — the Django tutorial mentions this in passing, but on a real project it pays off daily in the shell, the admin, and test failure output.

Step 2 — ScheduledClass: status, times, and two layers of validation

from django.conf import settings
from django.core.exceptions import ValidationError
from django.db import models


class ScheduledClass(models.Model):
    objects = VenueScopedQuerySet.as_manager()

    class Status(models.TextChoices):
        SCHEDULED = "scheduled", "Scheduled"
        CANCELLED = "cancelled", "Cancelled"
        COMPLETED = "completed", "Completed"

    venue = models.ForeignKey(
        "organizations.Venue",
        on_delete=models.CASCADE,
        related_name="scheduled_classes",
    )
    class_type = models.ForeignKey(
        ClassType, on_delete=models.PROTECT, related_name="scheduled_classes"
    )
    room = models.ForeignKey(
        Room, on_delete=models.PROTECT, related_name="scheduled_classes"
    )
    teacher = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.PROTECT,
        related_name="taught_classes",
    )
    starts_at = models.DateTimeField()
    ends_at = models.DateTimeField()
    capacity_override = models.PositiveIntegerField(null=True, blank=True)
    status = models.CharField(
        max_length=16, choices=Status.choices, default=Status.SCHEDULED
    )
    checkin_opens_minutes = models.PositiveIntegerField(default=30)

Why PROTECT on type, room, and teacher instead of CASCADE? Deleting a room with classes on the books must fail loudly, not cascade into silent data loss. CASCADE is for things owned by their parent (a venue owns its rooms); a class references its room, so the database should refuse the delete while references exist. Notice the teacher is the user model itself — there is no separate Teacher profile in v1; a teacher is a user with a teacher membership, which keeps lesson 2's tenancy story intact.

Times get validated twice, on purpose. The database gets a check constraint (the guarantee), and the model gets clean() (the friendly error):

    class Meta:
        constraints: ClassVar[list[models.BaseConstraint]] = [
            models.CheckConstraint(
                condition=models.Q(ends_at__gt=models.F("starts_at")),
                name="scheduled_class_ends_after_starts",
            ),
        ]

    def clean(self):
        super().clean()
        if (
            self.starts_at is not None
            and self.ends_at is not None
            and self.ends_at <= self.starts_at
        ):
            raise ValidationError({"ends_at": "Must be after starts_at."})

Two Django-version notes that bite here. First, Django 6.1 renamed the argument: CheckConstraint takes condition=, not the old check= — the old name raises TypeError. Second, clean() only runs when you call full_clean() (forms and the admin do; raw .save() does not). That is exactly why both layers exist: clean() gives humans a field-specific error, the constraint protects every writer including raw ORM calls. Test the constraint at the ORM seam and the message through full_clean() — you will see both styles in step 5.

Step 3 — The exclusion constraints (the heart of the lesson)

A house rule first: no double-booked rooms, no double-booked teachers, per venue. "Per venue" matters — the constraint must compare venue too, or one gym's schedule would block another's. Postgres expresses "no overlapping rows in this scope" with an exclusion constraint over a range. The range here is [starts_at, ends_at) — built with TSTZRANGE, half-open, so a class ending at 18:00 and the next starting at 18:00 share a bound without overlapping. Back-to-back classes are legal; overlapping ones are refused:

from django.contrib.postgres.constraints import ExclusionConstraint
from django.contrib.postgres.fields import RangeOperators
from django.db.models import Func, Q

# Range over [starts_at, ends_at): back-to-back classes share a bound but do
# not overlap, so no buffer logic leaks into the constraint.


def _overlap_range() -> Func:
    return Func("starts_at", "ends_at", function="TSTZRANGE")

Add both scopes to Meta.constraints, next to the check constraint. One shared range helper for both — not two handwritten range expressions — so room and teacher can never drift apart:

            ExclusionConstraint(
                name="no_double_booked_room",
                expressions=[
                    ("venue", RangeOperators.EQUAL),
                    ("room", RangeOperators.EQUAL),
                    (_overlap_range(), RangeOperators.OVERLAPS),
                ],
                condition=~Q(
                    status="cancelled"
                ),  # Status.CANCELLED; Meta cannot see the nested class
            ),
            ExclusionConstraint(
                name="no_double_booked_teacher",
                expressions=[
                    ("venue", RangeOperators.EQUAL),
                    ("teacher", RangeOperators.EQUAL),
                    (_overlap_range(), RangeOperators.OVERLAPS),
                ),
                condition=~Q(
                    status="cancelled"
                ),  # Status.CANCELLED; Meta cannot see the nested class
            ),

Read that predicate carefully — it is three decisions in one. EQUAL on venue and room (or teacher) scopes the rule: only rows in the same venue and room are compared. OVERLAPS on the range refuses shared time. And condition=~Q(status="cancelled") exempts cancelled classes entirely, so rebooking a freed slot never fights the ghost of the cancelled class. The comment is load-bearing Django trivia: Meta is evaluated before the nested Status class exists, so you must write the raw string "cancelled" — Status.CANCELLED raises NameError here.

Exclusion constraints need the btree_gist extension (scalar equality inside a range constraint requires GiST operator classes). Two places, each with a reason: the migration creates it so test databases get it automatically, and the Docker Postgres image creates it on first init so real databases get it too:

# scheduling/migrations/0001_initial.py — generated, then check this line survived:
django.contrib.postgres.operations.CreateExtension("btree_gist"),
uv run python manage.py makemigrations scheduling
uv run python manage.py migrate

Then read the generated SQL with your own eyes — this is the constraint that saves you at 6pm on Monday:

uv run python manage.py sqlmigrate scheduling 0001

Look for EXCLUDE USING gist with the tstzrange. If it is not there, stop: developing against SQLite is the usual cause (see step 0).

Step 4 — Capacity and append-only substitutions

Capacity is a property with a documented precedence — per-class override, else room, else type default — because all three exist in real gyms and exactly one must win:

    @property
    def capacity(self):
        """First non-null wins: override → room → type default."""
        if self.capacity_override is not None:
            return self.capacity_override
        if self.room_id is not None and self.room.capacity is not None:
            return self.room.capacity
        return self.class_type.capacity_default

Note self.room_id (not self.room): the raw foreign-key id avoids a database query when only the id is needed — a habit that keeps list views at a fixed query count (deliverable d2 below). And substitutions are append-only history — reassigning a teacher never rewrites who was originally booked:

class TeacherSubstitution(models.Model):
    """Append-only: reassigning never rewrites who was originally booked."""
    scheduled_class = models.ForeignKey(
        ScheduledClass, on_delete=models.CASCADE, related_name="substitutions"
    )
    old_teacher = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.PROTECT,
        related_name="+",
    )
    new_teacher = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.PROTECT,
        related_name="+",
    )
    reason = models.CharField(max_length=255, default="", blank=True)
    created_by = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.SET_NULL,
        null=True,
        blank=True,
        related_name="+",
    )

    def delete(self, *args, **kwargs):
        # Append-only history: substitutions are never removed.
        raise ValidationError("Teacher substitutions are append-only.")

related_name="+" means "no backwards relation" — nothing ever queries from a user to their substitutions, so no reverse accessor is created. And overriding delete() to raise is how the model defends its own invariant instead of hoping every caller remembers.

Step 5 — Prove the refusal, in tests

No shell session for this — the refusal is a guarantee, so it gets tests in tests/test_scheduling.py. You might reach for factory-boy here; don't. Three tiny helpers (about fifteen lines total) build exactly the objects this file needs, with names that read like the domain. A dependency that saves no lines is a dependency you maintain for nothing:

def _venue(slug="downtown"):
    org = Organization.objects.create(slug=f"org-{slug}", name=f"Org {slug}")
    return Venue.objects.create(organization=org, slug=slug, name=slug.title())


def _teacher(username="ada"):
    return get_user_model().objects.create_user(username=username)


def _class(venue, room, teacher, start, end, **overrides):
    class_type = overrides.pop(
        "class_type",
        ClassType.objects.get_or_create(
            venue=venue,
            name="Spin",
            defaults={"duration_min": 45, "capacity_default": 20},
        )[0],
    )
    defaults = {
        "venue": venue,
        "class_type": class_type,
        "room": room,
        "teacher": teacher,
        "starts_at": start,
        "ends_at": end,
    }
    defaults.update(overrides)
    return ScheduledClass.objects.create(**defaults)

The trick worth learning is in _class: get_or_create with defaults means ten tests can share one "Spin" type per venue without tripping the per-venue uniqueness rule, and **overrides lets any single test vary one field (like status=...CANCELLED) without a new helper. Then the tests read as intent — setup, refusal, and one comment naming the rule each case proves:

class TestNoDoubleBooking:
    def _setup(self):
        venue = _venue()
        room = Room.objects.create(venue=venue, name="Studio A", capacity=20)
        teacher = _teacher()
        return venue, room, teacher

    def test_overlapping_room_rejected(self):
        venue, room, teacher = self._setup()
        start = timezone.now()
        _class(venue, room, teacher, start, start + timedelta(hours=1))

        with pytest.raises(IntegrityError):
            # Same room, overlapping time, different teacher — still refused.
            _class(
                venue,
                room,
                _teacher("grace"),
                start + timedelta(minutes=30),
                start + timedelta(hours=2),
            )

Write all six refusal cases: overlapping room, overlapping teacher, cancelled-overlap allowed, back-to-back allowed, same slot in a different venue allowed, and ends-before-starts through full_clean. One pytest-django nuance: a failed insert poisons the test's transaction, so put each refusal as the last database write in its test (or wrap it in an inner transaction.atomic() savepoint) — anything you query after a bare IntegrityError will fail with it.

Step 6 — The list endpoint (bounded, scoped, cheap)

Install DRF (uv add djangorestframework) and register it — framework first, code second:

uv add djangorestframework

Add "rest_framework" to INSTALLED_APPS. Then the read view: GET /api/v1/classes?from=&to=. Three rules govern every list endpoint in this project, and this is where all three are established — later endpoints copy this shape:

1. Bounded. Never SELECT * — the client passes a date range, capped at 31 days, and anything outside it is a 400:

MAX_WINDOW = timedelta(days=31)


def parse_window_bound(value, default):
    if value is None:
        return default
    try:
        parsed = parse_datetime(value)
    except (ValueError, TypeError):
        raise serializers.ValidationError("Window bounds must be datetimes.")
    if parsed is None:
        raise serializers.ValidationError("Window bounds must be datetimes.")
    if timezone.is_naive(parsed):
        return timezone.make_aware(parsed)
    return parsed

Naive datetimes are assumed UTC rather than rejected — clients send wall times without zones constantly, and guessing UTC loudly (documented, consistent) beats 400ing half the requests. The except (ValueError, TypeError) covers both unparsable strings (parse_datetime returns None) and non-string input (raises TypeError).

2. Scoped. The queryset starts from the request's venue — never from a client-supplied id — using the for_venue manager from step 1. A ?venue= parameter that disagrees with the request venue is a 404, not a 403: to outsiders, other venues' rows do not exist (lesson 2's tenancy story — the isolation trio in deliverable d4 proves it: 404, 404, and 200 for the spanning member):

    def get_queryset(self):
        venue = self.request.venue
        param = self.request.query_params.get("venue")
        if param is not None and param != venue.slug:
            raise NotFound("No such venue.")
        venue_classes = (
            ScheduledClass.objects.for_venue(venue)
            .select_related("class_type", "room", "teacher")
            .order_by("starts_at")
        )
        start, end = self._window()
        return venue_classes.filter(starts_at__lt=end, ends_at__gt=start)

3. Cheap. select_related joins type, room, and teacher in the one query — without it, serializing N classes costs N extra queries. Prove it with assertNumQueries (deliverable d2): seed three classes, GET the list, assert the count stays flat as you add rows. Overlap the window with starts_at__lt=end, ends_at__gt=start (strict inequalities) so back-to-back classes at the edges are included exactly once.

Imports first (scheduling/views.py top) — every name below must resolve:

from datetime import timedelta
from typing import ClassVar

from django.db import IntegrityError
from django.utils import timezone

Permissions reuse lesson 2's pair — members may read, only staff may write — and writes translate database errors into API errors: an exclusion refusal on POST becomes a 400 naming the overlap, not a 500 with a Postgres traceback:

    permission_classes: ClassVar[list] = [
        IsVenueMember,
        IsStaffOrReadOnly,
    ]

    def create(self, request, *args, **kwargs):
        try:
            created = super().create(request, *args, **kwargs)
        except IntegrityError:
            # Exclusion constraint (room/teacher overlap) refused at the DB.
            raise serializers.ValidationError(
                "Overlaps an existing class for this room or teacher.",
            )
        return created

Wire the router (scheduling/urls.py, DefaultRouter registering classes) and include it under api/v1/ in the project urls. Then extend seed_demo with one room and one class — later lessons build on it — and finish with the capacity-shrink test (deliverable d3): shrinking capacity below the confirmed count keeps bookings and shrinks free seats only — which is why capacity is a computed property and never a stored column that could disagree with reality. (The booking half of that test arrives in lesson 4; here, assert the precedence chain itself: override beats room beats type default, with None all the way down.)

Exercises

1. Break it on purpose: open two shells, insert overlapping classes in the same room in both transactions before committing either. Confirm the second committer gets the IntegrityError — that interleaving is the bug Python-level checks cannot fix.
2. Time-zone trap: create a class at 18:00 Europe/Berlin and query it back. What does starts_at hold? Why does the constraint still work? (Hint: TSTZRANGE normalizes to UTC.)
3. Add a ?teacher= filter to the list endpoint following the ?venue= pattern, with a test for the mismatch case.
4. Make the window error tell the truth: request from after to and a 60-day span, and check both messages name the actual problem.
