Aggregators

Win: a stranger's platform books your seats — within allotment, idempotently, billed to them, never touching member passes.

Phase 2 starts here, and only here: partners multiply every booking-path bug onto someone else's platform, so this lesson is gated on all eleven before it. An aggregator (think ClassPass) books seats under contract terms — a seat allotment per class, its own cancel cutoff, commission — without member passes and without member logins. New app (startapp aggregators), because this is a new bounded context with its own auth, not an extension of the member one.

Step 1 — Partner models and token auth

Aggregator (slug, hashed token, seat allotment, contract cutoff, commission, active, webhook URL/secret, plus a service user — a real User row that stands in as the booking's member, created unusable-passworded so it can never log in), AggregatorBooking (partner + external id → booking, unique together), AggregatorEventLog (every inbound call — reconciliation evidence). Authentication is per-partner tokens over a separate router, POST /api/v1/aggregators/<slug>/bookings, with three rules that all matter: hash the presented token with sha256 and compare with hmac.compare_digest against the stored hash — never user passwords, never plain == (plain equality leaks via timing; compare_digest is the stdlib answer). Rotate by saving a new hash — the old token 401s everywhere immediately, which is also its test. Throttle per partner, and note the gap honestly: failed authentications carry no partner identity, so throttling starts after auth — brute force is infeasible against 256-bit tokens, but know where your rate limit begins.

Step 2 — Book within allotment, idempotently

Enforce min(allotment, free seats), then reuse lesson 4's book_seat — same seats, same locks, two new keyword arguments (spend_credits=False, source="aggregator:<slug>"): aggregators are just another channel, and inventing a second booking write would split the seat-lock discipline. The idempotency pattern deserves memorization, because the naive version has a named bug:

link = AggregatorBooking.objects.filter(
    aggregator=partner, external_id=external_id
).first()
if link is not None:
    if link.booking.scheduled_class_id != klass.pk:
        raise DuplicateBooking("external_id already books another class.")
    return link.booking, False
with transaction.atomic():
    booking = book_seat(...)
    # Count AFTER the seat lock is held: a parallel retry serializes
    # behind us and sees our booking, so the cap holds.
    held = AggregatorBooking.objects.filter(...).count()
    if held + 1 > partner.seat_allotment:
        raise AllotmentExhausted("Allotment exhausted.")
    try:
        AggregatorBooking.objects.create(...)
    except IntegrityError:
        # Lost the race; return the winner.
        ...

Never get_or_create(defaults={"booking": book_seat(...)}) — arguments evaluate before the call, so the seat would book on every retry, hit or not. And the count goes after the lock: counted before, two parallel retries both see zero and both book past an allotment of one. Their late-cancel uses the contract cutoff, billed to nobody's passes (there are none to touch), and partner cancels promote the member waitlist exactly like member cancels — two channels, one behavior. Log every request first: replaying the event log must reproduce booking state, and that replay is the reconciliation test.

Step 3 — Outbound feed, webhooks, and rotation

Read-only GET .../schedule?from&to (bounded like every list before it) serves a slim serializer — no staff usernames leave the building; partners get ids and names, never login identifiers. Change webhooks go out over Celery with backoff retries, HMAC-signed with the per-partner secret; verify signatures in tests, both directions (valid verifies, tampered rejects). Then the four acceptance checks that close the course: same external_id twice → one booking; past allotment → 409; rotated token → old 401s; bad webhook signature → rejected; event-log replay → identical state.

Exercises

1. Remove the class-mismatch guard and reuse one external id across two classes. Describe the customer-visible damage.
2. Move the allotment count before the lock and run parallel retries. Count the over-bookings.
3. Cancel a partner booking with members waiting. Who gets the seat, and which line decides it?
4. Design the next channel (front-desk walk-ins?) on top of book_seat. What parameters does it need, and what must it never touch?
