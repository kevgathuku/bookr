1. Tenancy: Organization → Venue, duties in OrgRole

Organization is the tenant root (the business). Venue is one location under it (organizations/models.py; slugs unique per org). There is no per-venue database: every tenant-scoped row carries its venue/organization FK; middleware resolves the request venue, and venue-scoped querysets (VenueScopedQuerySet, via as_manager()) scope model reads to it.

Duties live in OrgRole, never on User. One user holds many rows: member at venue A, teacher at venue B. venue=None means the role applies org-wide. Roles: member, teacher, frontdesk, manager, owner. Django Groups are never consulted (ADR-0005); capabilities derive from roles (organizations/capabilities.py, permissions.py).

2. Money: Plan × Entitlement × Validity → Membership → CreditLedger

Plan is the product definition. plan_type (monthly/credit_pack/drop_in/complimentary/aggregator/staff) is a sales label only — behavior comes from two axes:

  • Entitlement: unlimited (never charged, balance is NULL) or credits (charged per booking, positive credits_included).
  • Validity: open_ended (NULL expiry), fixed_duration or recurring (both need duration_days > 0; renewal is manual re-purchase).

Both axes are DB check constraints (plan_credits_match_entitlement, plan_duration_match_validity) mirrored in Plan.clean() for friendly admin errors.

Membership = one user × one plan × one date window. One purchase = one membership — never top up: a second purchase mints a new row (topping up would inherit the old expiry and hide what was bought when). credits_remaining is a cached balance (NULL = unlimited); valid_until NULL = never expires. payment_ref carries the incident key for grants.

CreditLedger is the append-only truth (ADR-0002): every movement is a row (purchase, booking, refund, forfeit, expiry, adjustment); rows are never edited or deleted (save() guards). The balance is whatever the rows sum to — reconcile_ledger fails loudly on drift. All writes funnel through passes/services.post_entry(), which locks the row, refuses zero deltas and unlimited rows, and enforces the floor.

3. Booking flow: one transaction, one payer, one stamp

Entry: booking/services.book_session(). Everything happens inside one SELECT … FOR UPDATE on the session row, so concurrent requests serialize per session. Retries are safe: one active booking per member+session (partial unique one_active_session_booking), so a repeated request raises DuplicateBooking, never a double charge.

  1. Lock + validate — session open (not started/cancelled), no duplicate, seats left (full GROUP sessions queue instead when waitlist=True; private sessions raise).
  2. Pick the payer — _paying_membership(): unlimited first, else first-expiring credit pack covering the price (valid_until nulls-last). Explicit memberships are validated (owner, org, dates).
  3. Stamp the price — credits_spent on the booking (0 for unlimited/comped; waitlisted and held rows always stamp 0).
  4. Spend once — spend_for_booking() → post_entry() writes the BOOKING row and bumps the cache in the same transaction. CreditInsufficient rolls everything back.

A same-member double-submit race is mapped to DuplicateBooking (the unique one_spend_and_refund_per_booking guard turns a would-be double spend into an IntegrityError first).

4. Cancellation, refunds, waivers

Entry: booking/cancellations.cancel_booking(). Every exit writes one immutable CancellationRecord pinning session, member, plan, policy, actor and cause — history is never rewritten.

  1. Resolve the policy — booking/policies.resolve_policy() picks the most specific CancellationPolicy (venue → category → plan_type); late = inside late_cancel_hours of start.
  2. Apply the outcome — on-time (or waived, or staff override): full refund via _refund() (exact stamp, same transaction); late + LOSE_CREDIT: forfeit (no rows — forfeit is the absence of a refund); late + STRIKE: stamp stands, strike counted (30-day window).
  3. Held seats release as UNCLAIMED (nothing was charged, nothing returns) and session cancels refund every active stamp.

Forgiveness never rewrites: inline waivers stamp the record at creation; retroactive waivers post a compensating ADJUSTMENT row linked to the record (waive_record(), idempotent per record), capped at credits_spent − already refunded. Zero-owed records (monthly/comped seats) raise — there is nothing to compensate. Desk corrections use POST /ledger/adjust/ (reason required, floor enforced); grants are not adjustments — the desk mints a new complimentary membership via POST /ledger/grants/ (idempotent per incident key), never tops up.

5. Waitlist: join → promote (hold) → confirm / sweep

  1. Join needs a valid membership but moves no money and writes no ledger row.
  2. Promote (promote_next(), head-only, FIFO) seats the longest waiter as HELD with a deadline (HOLD_WINDOW_MINUTES = 60); lapsed heads stay queued and the seat stays open.
  3. Confirm (confirm_booking()) charges the pass and flips Held → Booked. Sweep (sweep_expired_holds) releases lapsed holds as unclaimed and passes the seat on. Promotion and the sweep are shared tasks (booking/tasks.py) so workers and the web process share them.

6. Aggregators: the partner channel

Partners authenticate by API token (AggregatorAuthentication), never as users. Each partner owns a machine account (svc-<slug>: unusable password, blank email, no roles) and exactly one comp vehicle membership that carries no money and no rows.

  1. Book (book_partner_seat()): idempotent on (aggregator, external_id) via AggregatorBooking; books through the same book_session(spend_credits=False) as members (amount 0, no ledger rows). The real gate is the seat allotment, counted after the seat lock so over-limit raises roll the booking back too.
  2. Cancel delegates to cancel_booking() (same unified record); moves no money (late partner cancels assert zero ledger rows).
  3. Every call is logged to AggregatorEventLog; webhooks fire on create.

The vehicle reuses one membership forever (the documented exception to one-per-purchase: reuse corrupts nothing — no balance, no rows). It is also the reason the door has two arms (below).

7. Door: the read-only verdict

Entry: access/services.decide(). Read-only: moves no credits, changes no bookings. Per-attempt logging, 60s verdict cache, fail-closed on DB outage.

  1. Active pass — unlimited valid within dates, or credit balance > 0 within dates.
  2. Live booking — a BOOKED seat in the entry window (this is how partner guests and zero-balance members get in).
  3. Staff — duty roles via capabilities.
  4. Otherwise: no_access. Passback replays the last verdict inside the window.

8. Invariants (do not break)

No guest path. Every booking holds a paying membership FK (PROTECT) — drop-ins, comps and partner seats included.
One purchase = one membership. Never add credits to an existing row; mint a new membership (+ plan if terms differ) with its own PURCHASE row.
One writer for money. All balance moves go through post_entry(); the cache is derived, and reconcile_ledger proves it.
NULL means unlimited / never-expires — on balances and on dates. Every comparison must be NULL-safe.
History is append-only. Ledger rows and cancellation records are never edited or deleted; forgiveness is a linked row.
Refunds return the stamp. Exactly credits_spent, never a fresh price lookup — repricing mid-sale stays correct.
Forfeit is the absence of a row. Do not invent FORFEIT rows; waiver math depends on the gap.
Zero-amount bookings write zero rows (monthly, comped, held, waitlisted). The audit trail for those lives in status transitions, not the ledger.
